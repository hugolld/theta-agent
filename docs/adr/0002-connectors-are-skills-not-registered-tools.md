# 0002 — Connectors ship as Theta-owned skills, not registered tools

- **Status**: accepted (2026-10-12)
- **Context**: M2 connects PubMed, arXiv, and Semantic Scholar (spec #16). Two shapes could carry a connector: Theta-owned skill material (SKILL.md doctrine + stdlib helper scripts) or a registered pi tool (`pi.registerTool` + TypeBox schema in an extension). A two-arm contest settled it before the strike: one capability (PubMed esearch + esummary) built both ways against an identical behavior spec and description, then six one-shot dogfood sessions, interleaved A,B,A,B,A,B, with the vendored `paper-lookup` present and untouched in both arms. The decision rule was pre-registered before any run (m1-closeout grilling handoff): if routing reliability, contract enforcement, and evidence quality come out comparable, the skill layer wins by simplicity; a tool win requires a visible, repeatable advantage on at least one axis. Primary source: `VERDICT.md` at the tip of `prototype/m2-shape-contest` (session dirs and per-run analysis on that branch).
- **Decision**: Connectors are **connector skills** (GLOSSARY): Theta-owned SKILL.md doctrine plus Python-stdlib helper scripts under the skill's directory, with enforcement in code the model calls. The contest met its pre-registered rule — routing was 3/3 unprompted per arm (the incumbent never picked, 0/6), enforcement ran 18/18 model-initiated retrievals through arm code with zero hand-rolled curl, and evidence was fully auditable both ways — so no visible, repeatable tool advantage existed on any axis, and the skill layer wins on simplicity: no TS runtime surface, no peer imports, no packaging change (pi scans the skills directory).

## Considered options

- **Registered pi tool (arm B)** — arguments schema-validated from the first call; ~7–8 s faster first use (the saved SKILL.md read — a latency nicety, not a reliability gain); structured `details` in tool-result records, nicer for machine audits, but the repo's own dogfood auditor attests the skill shape end-to-end, so the campaign's evidence standard is met both ways. Its pacing bucket spans the session where a script's spans one invocation — the one structural edge found, never observed live (calls ran 7–16 s apart) and unfixable by a stateless script; recorded as a residual, not a repeatable advantage. Its build failure mode is loud where an invalid SKILL.md description silently drops the skill — the sharpest asymmetry, closed for the skill layer by the real-YAML frontmatter guard in `test/skills-library.test.mjs` (#22), not by the shape.
- **MCP server per connector** — the same registration question one layer up; out of scope for M2's literature sources. M4's compute gateway returns to gateway-shaped integration on its own terms.

## Consequences

- Doctrine (when to call) stays in SKILL.md; enforcement (how: pacing, in-200 error detection, redaction) stays in the scripts. The script invariants that keep connectors interchangeable: `docs/agents/connector-scripts.md`.
- Connector skills need no manifest entry and keep the package free of TS runtime surface for connectors; `theta-lit-search` added none.
- Per-invocation script pacing is an accepted residual: parallel shells can in principle burst past a rate limit, and a stateless script cannot fix it — serialize connector work instead.
- The evidence base is n = 3 per arm, one model, one provider, one day; routing was unanimous (6/6) — strong for this setup, not proof at scale.
- **Revisit trigger**: the M4 compute gateway. Literature connectors are not revisited by it; compute-side integration is stateful and long-running where literature connectors are stateless request/response, and if the gateway work shows the tool layer's session-spanning state or structured records earning their cost there, the contest shape re-runs on that question. Closed 2026-10-20 by ADR 0004: that state and those records earn their cost in the gateway itself, and the contest does not re-run.
